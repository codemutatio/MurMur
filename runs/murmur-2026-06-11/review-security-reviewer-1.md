## Security Review

**Attack surface summary:** This change introduces a new macOS process that records the owner's microphone all day, transcribes speech locally via mlx-whisper, writes daily Markdown transcripts, and optionally routes audio to the OpenAI API. The newly exposed surface consists of: (1) a config.toml file whose directory and path values flow into subprocess calls and filesystem operations; (2) an osascript notification channel whose message strings include OS error text and disk-free integers; (3) the spool directory containing transient WAV segments that are parsed by the worker thread; (4) a macOS Keychain and environment-variable pathway for the OpenAI API key; (5) model weight download via huggingface_hub on first run; and (6) a launchd plist rendered by string formatting without XML escaping. The privacy guarantee (no outbound network during normal operation) was verified directly in mlx_whisper's `load_models.py` — the `snapshot_download` call is gated on `not model_path.exists()`, so a valid local snapshot path suppresses it entirely. `load_silero_vad()` loads from the pip wheel's bundled data with no network call. When `api_fallback = false` (default), `OpenAITranscriber` is never instantiated and no network object is constructed. Transcript text never flows into log messages, notification content, or error strings. The API key is never passed via subprocess argv and is never logged.

| Sev | Location | Finding (with attack scenario) | Remediation |
|-----|----------|--------------------------------|-------------|
| Minor | `src/murmur/mac/launchd.py:39,57,59` | **Plist XML injection via unescaped path strings.** `render_plist` interpolates `murmur_bin`, `log_path`, and each element of `program_args` directly into the plist XML via f-string without XML-escaping. In production `install_agent()`, `murmur_bin` comes from `shutil.which("murmur")` (PATH-derived) and `log_path` is a hardcoded subpath of `~/Library/Application Support/Murmur/`. A macOS username or PATH component containing `<`, `>`, or `&` — unusual but valid — would produce a malformed plist. No remote exploitation path exists; the owner's own environment must be adversarial. The `program_args` override accepted by the public API additionally allows callers to inject arbitrary XML into `<string>` elements. Attack: owner configures `$PATH` to include a directory named `</string><key>RunAtLoad</key><true/>` and the resulting plist would load the agent even when RunAtLoad was set False. | Replace f-string interpolation with proper XML escaping (Python's `html.escape()` applied to each interpolated value, or use `plistlib` to generate the XML programmatically). |
| Minor | `src/murmur/transcribe/worker.py:101` | **Unhandled `ValueError` from malformed spool filename crashes worker thread.** `parse_segment_start(wav_path)` at line 101 splits the filename on `-` and parses integers. It is called outside any `try/except`, so a `*.wav` file in the spool directory whose stem does not match `YYYYMMDD-HHMMSS-mmm` raises `ValueError` that propagates through `_process()` to `run()` (no top-level handler), terminating the transcription thread. The spool directory is `~/Transcripts/spool/` with default macOS `755` permissions — readable but not writable by other users. However, the owner could accidentally copy an arbitrary `.wav` file there. More relevantly, `list_spool()` returns all `*.wav` files including any temporary `.wav.tmp` that survived a crash rename. A `.wav.tmp` file would also fail parsing (stem contains extra dots). Attack: owner places any arbitrarily-named `.wav` file in spool (e.g., a reference recording), `list_spool` picks it up, `parse_segment_start` raises, worker thread dies, transcription silently stops. | Wrap `parse_segment_start` in a `try/except` inside `_process()` and log an error + skip the file on failure (consistent with the `load_wav` handler pattern above it at lines 94–98). |
| Minor | `src/murmur/transcribe/models.py:65–68` | **Marker-file trust skips re-verification of model weights after download.** After a successful sha256 check, `ModelManager` writes a JSON marker to `~/.cache/huggingface/murmur-model-verified-{model}.json`. On all subsequent starts, if the marker exists, the sha256 check is skipped entirely — the local weights are used without re-verification. Any local process running as the same user can create the marker file, causing a replaced or corrupted snapshot to be loaded silently without triggering the checksum error path. Attack: another process replaces weights in the HuggingFace cache directory and creates the marker file; the next Murmur start loads the tampered weights. Within the single-user personal-tool threat model this is a low-probability path, but it means the "verified" guarantee is weaker than the code suggests. | Store the sha256 hash of each verified file inside the marker JSON and re-verify the hash on startup (a fast in-process check; no HF API call needed). If the stored hash mismatches the local file, fall back to full re-verification. |
| Minor | `src/murmur/output/retention.py:50–64` | **Retention pruning follows symlinks.** `transcripts_dir.iterdir()` follows a symlink if `transcripts_dir` itself is a symlink. If `~/Transcripts` is a symlink to a directory the owner also uses for other purposes, a file in that directory matching `YYYY-MM-DD.md` and older than `retention_days` days would be deleted. The owner controls `storage.transcripts_dir` in config and would have to deliberately point it at a symlink. Within the stated threat model (malicious config) this is a valid path. Attack: attacker modifies `config.toml` setting `transcripts_dir` to a directory containing important files named like `2024-01-01.md`; those files are deleted at next launch. | Either resolve the path with `.resolve()` before use in retention pruning, or document in README that `transcripts_dir` must not be a symlink to a shared directory. |
| Minor | `pyproject.toml:7–18` | **All runtime dependencies pinned only with `>=` lower bounds; no upper bounds or lock-file pins.** `torch>=2.0`, `openai>=1.0`, `huggingface-hub>=0.23`, `mlx-whisper>=0.4.1`, `silero-vad>=5.1` are all wide ranges. The installed versions (torch 2.12.0, openai 2.41.1, huggingface-hub 1.19.0) are current and no known CVEs were found against these versions as of 2026-06-12. However, an unattended `uv sync` after a supply-chain compromise of any of these packages would install a malicious version silently. For a personal tool this is accepted risk, but it is worth noting. The `rumps 0.4.0` dependency is stale (last release ~2023) as noted in the plan. | For long-term use, pin to the versions in `uv.lock` (already generated by uv) and review updates intentionally. No immediate action required; this is informational for this audit. |

No blockers. No majors. Five minors logged.
