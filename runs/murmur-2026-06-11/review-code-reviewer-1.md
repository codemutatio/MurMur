| **Major** | `src/murmur/audio/source.py:75` | `self._dropped_frames += 1` is written from the PortAudio C-callback thread without any lock. The callback runs on a system-level C-thread, not the capture-engine thread. `_dropped_frames` is a plain Python `int`. Although CPython's GIL protects against torn writes on a single `+=`, the read in the `dropped_frames` property at line 119 has no memory-ordering guarantee across C-threads and the operation is non-atomic with respect to the counter ever being reset (it is never reset, but callers could read stale values). More critically: ADR-1 says "The PortAudio callback thread does exactly one thing: `queue.put_nowait`". Writing to `self._dropped_frames` is a second thing, and it touches mutable state on a thread that is not supposed to own any state. The counter is never surfaced to `StatusBoard`, so it is dead output for the user — but it is still a thread-ownership violation. | Move the drop counter into the capture-engine thread (read queue size delta or use a `threading.atomic`-style pattern). Or remove it entirely; the StatusBoard `increment_errors` path already covers lost frames. |
| **Major** | `src/murmur/audio/segmenter.py:127–134` | The silence-close condition and the force-split condition are mutually exclusive via `elif`. If `_consecutive_silence >= _silence_frames` is true at the same tick that `len(_active_frames) >= _max_frames` is also true (which can happen in the one-frame window where both conditions first become satisfied simultaneously), the force-split branch is never reached and the silence-close fires instead. For the 120 s max boundary specifically: if silence happens to accumulate at exactly the moment the active buffer also hits 3750 frames, the segment is closed by the silence path (correct). The only real issue is the inverse: after a force-split the remainder buffer immediately re-enters ACTIVE with `_last_speech_idx = 0` (line 197). If the remainder is then immediately >= max_frames on the next push call — which is possible if split_idx is 0 (the quietest frame is the very first frame) — the next push will produce another split with a 1-frame part1. There is no lower-bound guard on `split_idx`, so if every frame has the same RMS, `argmin` returns 0, and the code emits a 1-frame (~32 ms) segment followed by re-entering ACTIVE with the rest. This 32 ms segment is 512 samples — fine for the hallucination guard to drop — but it violates the expectation that force-split produces "each ≤ 120 s" meaningful segments. AC-13 does not test this degenerate case. | Add a minimum split position guard: `split_idx = max(1, int(np.argmin(rms_values)))` so part1 always has at least one frame's worth of audio. |
| **Major** | `src/murmur/audio/engine.py:226` | `self._work_q.put(wav_path)` is an unbounded blocking call. The plan contract specifies `work_q` as an unbounded `queue.Queue()` (no maxsize), which means `put()` never blocks — but if the worker thread is dead or stuck in a 30 s backoff sleep (E-10 path), the work queue grows without bound. The capture engine will continue enqueuing WAVs indefinitely, piling up spool files with no bound. This violates the plan's "queue back-pressure" intent — the plan's architecture diagram says "work_q (queue.Queue[Path])" and the risk table acknowledges queue-drop counters as a signal for MV-21. No back-pressure mechanism or queue-depth cap is implemented. On a long-running daemon this can exhaust spool disk space. | Use `work_q = queue.Queue(maxsize=N)` (e.g. 500 items) with a non-blocking `put_nowait` + drop path in `_emit_segment`, mirroring the frames_q pattern. Alternatively document the accepted risk explicitly in implementation-notes. |
| **Major** | `src/murmur/transcribe/worker.py:109–156` | The retry loop for local transcription failures is an unbounded tight loop with no sleep between local retries. Lines 127–129: when `consecutive_local < max_local_failures`, the code does `continue` immediately — no sleep, no back-off. On a model crash or persistent OOM this will spin at CPU speed until the failure count reaches 3. With the default `max_local_failures=3` this is only three tight iterations, which is acceptable in itself, but if `max_local_failures` is set high (e.g. in a test or future config) this becomes a CPU-burn loop. More importantly: the inner retry loop catches only `TranscriptionError`. Any non-`TranscriptionError` exception (e.g. a numpy or mlx panic, an `AssertionError` from mlx internals, a `MemoryError`) escapes the `try/except TranscriptionError` entirely and propagates up to `_process`, where it is also not caught — it will propagate to `run()`, which has no outer exception handler, silently killing the worker thread (daemon=True, so no visible crash). This means a single unexpected exception in any transcription call permanently kills the worker thread for the lifetime of the process. | Wrap the entire `_process` call in `run()` with `except Exception as exc: _log.error(...)` to keep the worker alive. Add a `time.sleep(0.1)` or similar between local retries to prevent tight spin. |
| **Major** | `src/murmur/audio/engine.py:196–200` | The segmenter exception handler at lines 197–200 catches `Exception` but swallows it and continues — this is correct for resilience. However, there is no outer exception handler on the `run()` method of `CaptureEngine`. Any exception in the device poll block, the `flush_and_close` call, the `source.open()` call, or the `default_device_signature()` call that is not explicitly caught by the existing `try/except AudioSourceError` block will bubble up to `run()` and silently terminate the capture thread (daemon=True). For example: `write_segment_wav` can raise `OSError` for the E-14 disk-full case, which is caught, but an unforeseen exception type from `sd._terminate()` or `sd._initialize()` would not be. A daemon thread killed by an unhandled exception simply stops; the menubar continues showing "●" (recording) while no audio is being captured. | Wrap the `while not self._stop_event.is_set()` body in an outer `except Exception` that logs and continues (with a brief sleep to avoid fast spin on repeated errors). |
| **Minor** | `src/murmur/transcribe/guard.py:64–65` | The filler-phrase matching uses `text.lower().rstrip(".")` for `normalized`, then checks `if normalized in FILLER_PHRASES or text in FILLER_PHRASES`. The second branch `text in FILLER_PHRASES` is redundant: `text` was just `.strip()`-ped but not lowercased. The FILLER_PHRASES set contains lowercase entries only (e.g. `"thank you."`, `"."`, `""`). A mixed-case `text` like `"THANK YOU."` will not match the second branch — only the first (normalized) branch catches it. The second branch can match only if `text` itself happens to already be lowercase AND in the set. This means the `or text in FILLER_PHRASES` check is dead code for any text that is not already all-lowercase AND in the set, since `normalized = text.lower().rstrip(".")` would have already matched it. It is not wrong (it is just unreachable for uppercase input), but it adds confusion. | Remove the `or text in FILLER_PHRASES` branch; rely solely on `normalized in FILLER_PHRASES`. |
| **Minor** | `src/murmur/audio/segmenter.py:21–22` | `_PRE_ROLL_FRAMES` and `_POST_ROLL_FRAMES` are computed at module level but are never referenced anywhere in the module. The class recomputes `self._pre_roll_frames` and `self._post_roll_frames` from `cfg.pre_roll_s` in `__init__`. These module-level constants are dead code. | Remove the module-level `_PRE_ROLL_FRAMES` / `_POST_ROLL_FRAMES`. |

| **Minor** | `src/murmur/audio/spool.py:64–85` | `parse_segment_start` uses `stem.split("-")` which assumes exactly three segments (`date_part`, `time_part`, `ms_part`). A WAV filename that collides with a temp file prefix or is manually placed in the spool with a different naming convention will raise `ValueError` with an opaque "not enough values to unpack" message. No error handling guards the caller in `TranscribeWorker._process` (line 101: `start_at = parse_segment_start(wav_path)` has no try/except).
